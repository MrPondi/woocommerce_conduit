# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Frappe/ERPNext app (`woocommerce_conduit`, requires `erpnext`) that syncs WooCommerce items, item prices and orders with ERPNext. It is a slimmer rewrite related to the `woocommerce_fusion` app that sits beside it in `apps/`. Fusion has features Conduit does not: batch/queue API, field transforms, two-way Item sync. Conduit's stock sync (`tasks/stock_update.py`) and Item form buttons (`public/js/item.js`) are ported from Fusion. Do not assume Fusion code can be copied as-is, because the sync classes differ.

The repo root is the app dir; the Python package is the nested `woocommerce_conduit/` folder. The Frappe module is `woocommerce_conduit/woocommerce/`, which holds all doctypes.

## Commands

Run from the bench root (`/workspace/development/frappe-bench`), not the app dir. The site used for development is `conduit.localhost`.

```bash
bench --site conduit.localhost migrate                       # after doctype JSON / patch changes
bench --site conduit.localhost clear-cache
bench --site conduit.localhost set-config allow_tests true   # once, needed for tests
bench --site conduit.localhost run-tests --app woocommerce_conduit
bench --site conduit.localhost run-tests --module woocommerce_conduit.woocommerce.doctype.woocommerce_product.test_woocommerce_product
bench --site conduit.localhost run-tests --doctype "WooCommerce Product"
```

Lint/format (run in the app dir): `pre-commit run --all-files`. It uses ruff (lint, including the pyupgrade rules, import sort and format), eslint and prettier. pre-commit only checks files git tracks, so `git add` new files first.

- The lint tools follow Frappe core's own `.pre-commit-config.yaml` and the `bench new-app` template of the installed Frappe (`frappe/utils/boilerplate.py`): pre-commit-hooks 6.0.0, ruff 0.14.10, prettier 2.7.1, eslint 8.44.0. The `[tool.ruff]` ignore list follows the template too. Bump them when Frappe does, and never ahead of it, so the app formats and lints like Frappe.
- If pre-commit fails to install Node for prettier or eslint, with nodeenv's `invalid literal for int()` on a version like `27.0.0-alpha`, upgrade pre-commit's nodeenv to 1.12 or later (`uv tool upgrade pre-commit`). nodeenv 1.11 takes the Node prerelease that nodejs.org lists first for the latest version. pre-commit downloads its own Node when the only one installed is under the home directory, as nvm's is.
- Python style: **tabs** for indentation, double quotes, line length 110, target py314, the Python Frappe v16 needs (see `[tool.ruff]` in `pyproject.toml`).
- CI (`.github/workflows/ci.yml`) installs the app on a fresh bench of the pinned Frappe and ERPNext versions (`TEST_AGAINST_FRAPPE_VERSION`, `TEST_AGAINST_ERPNEXT_VERSION`; Python 3.14, Node 24) and runs `run-tests --app woocommerce_conduit`. `linter.yml` runs Frappe Semgrep rules and pip-audit.

## Architecture

### Virtual doctypes backed by the WooCommerce REST API

`WooCommerce Product` and `WooCommerce Order` are **virtual doctypes**. They have no DB tables. They subclass `WooCommerceDocument` in [woocommerce/woocommerce_api.py](woocommerce_conduit/woocommerce/woocommerce_api.py), which implements `load_from_db`, `get_list_of_records`, `get_count_of_records` and `db_update`. `db_insert`/`delete` are no-ops.

- `db_update` PUTs only the fields that differ from `_doc_before_save` (which `save()` re-fetches from WooCommerce), filtered and shaped by the subclass's `before_db_update`, and stores the returned `date_modified`. `write(changes)` sends changes without the reload `save()` does. The price and stock pushes compare with the record they just loaded (`get_changes`) and only write what differs, because WooCommerce dates every save as a change and fires its product-updated hooks. `WooCommerce Product` only ever writes the price and stock fields in `writable_fields`. `WooCommerce Order` only writes `status`. Frappe's length/select validators are disabled on these doctypes, because WooCommerce decides what is valid.
- A record's `name` is `"{server_domain}~{wc_id}"` (`WC_RESOURCE_DELIMITER = "~"`). Use `generate_woocommerce_record_name_from_domain_and_id` and `get_domain_and_id_from_woocommerce_record_name` rather than building or parsing it by hand.
- `WooCommerceDocument.__init__` takes the `WooCommerceAPI` clients of the **enabled** servers from `get_api_clients`, and throws `SyncDisabledError` if none exist. The clients are built once per request or job (`request_cache`, cleared when a server is saved), as each needs the server's passwords decrypted.
- WooCommerce orders each server's records: by the list's first sort field when it can (`orderby_map` and `COMMON_ORDERBY_MAP`, which has Last Updated for products and orders alike), else by date, newest first, which is then asked for explicitly. An ordered list of several servers is merged in that order: each server is read from its first record to the end of the page, and the merged records are cut to the page (`_get_merged_records`), so page n reads n pages of every server. An unordered list, or one of a single server, reads the servers one after the other, as one list (`_get_records_in_turn`): a server whose records all lie before the offset is skipped by its `x-wp-total`, and no server is asked once the page is full. The syncs read that way, as they don't order. The page is then ordered as asked (`sort_records`: a name orders by its id as a number, text regardless of case). Only Frappe's list and report views send an order and a `start`. `page_length` is how many records to return, fetched `per_page` (at most 100) a request. `servers` limits the servers read.
- `load_from_db` raises `frappe.DoesNotExistError` on a 404, which isn't logged as an error.
- Filters are normalised with Frappe's `Filters`, so a dict or lists of 3 or 4 all work (`map_frappe_filters_to_wc_params`). A `woocommerce_server` filter, or one on record names, picks the servers to read (`get_servers_from_filters`). `name`/`id` become `include`, and the date fields become after/before (`Between` covers whole days). Any other filter is an error, as dropping it would return unrelated records. `get_count` uses the same filters.
- Each subclass declares `resource`, `field_setter_map`, `field_getter_map` (Frappe fieldname → WC fields it needs), `orderby_map` and `mandatory_wc_fields`. Only the WC fields needed for the requested Frappe fields are requested (`_fields`). When you add a field to a virtual doctype, update these maps so it is actually fetched.
- `WooCommerceAPI` wraps the `woocommerce` client of one server. A request that the shop answers with a 429 or a 5xx, or whose connection drops, is sent again up to 3 times, after 1, 2 and 4 seconds (a little longer at random) or the shop's `Retry-After` when longer, while the next try can start within 2 minutes of the first, or 10 seconds in a web request (`get_retry_delay`). A POST is only sent again after a 429, as after a 5xx the shop may have made the record. Timeouts and SSL errors aren't retried. The loop is around `super()._API__request`, so the client signs each try anew. Its failed requests, every retried try among them, and all of them when the server has `log_all_requests` ticked, are kept as Frappe **Integration Requests** (service "WooCommerce", linked to the server). They are written through `frappe.deferred_insert`, so a rolled-back sync keeps its log. They show up within 15 minutes, and Log Settings clears them after 90 days. Nothing is logged under `frappe.in_test`.
- Complex values (dicts/lists) are JSON-serialised into JSON fields. `after_load_from_db` on each subclass flattens or prettifies them for the form.
- `WooCommerce Product.get_list` also fetches variations. Its behaviour (variation fetching, batch size, max variations) is driven by `WooCommerce Settings`. Lists are never cached, so they show what WooCommerce has now.

### Sync layer (`tasks/`)

- Each sync is a class of its own (`SynchroniseItem`, `SynchroniseSalesOrder`, `SynchroniseItemPrice`), with no shared base class. Each loads the servers it needs with `get_cached_doc`. `tasks/sync.py` has `record_sync_time`.
- `sync_items.py` has `SynchroniseItem`, which syncs WC products **into** ERPNext Items, one way. A product is pulled **once**: a missing Item is created (with its regular and sale price as Item Prices) when an order needs it or on a manual sync, and a linked Item is only updated again with `force_update` (the Sync buttons). On a server that names Items by SKU, a product is linked instead to the enabled Item whose code or barcode is its SKU (`find_item_by_sku`, a template only for a variable product). That Item keeps its fields and takes the product's prices only for the price lists it has none in (`link_item`). A code that is taken gets a number (`append_number_if_name_exists`), as ids repeat across shops. One Item can be linked to several shops, and each shop keeps its own name, description, etc., so Item fields are never written back to WooCommerce. Only prices (`sync_item_prices.py`) and stock (`stock_update.py`) go from ERPNext to WooCommerce, each switched per `WooCommerce Server` (`enable_price_list_sync`, `enable_stock_level_synchronisation`) and per Item connection (`Item WooCommerce Server.enable_sync`, "Sync Prices and Stock", default on). Stock is the sum of the server's `warehouses`, a group counting with the warehouses under it (ERPNext's `get_child_warehouses`). The regular price is the Item Price ERPNext would charge today (`get_item_prices_for_stock_uom`: valid today, in the stock UOM, for anyone). The sale is the running one that started last, else the next one to start, which WooCommerce schedules (`pick_sale`). With the server's `sync_in_sales_uom`, an Item that sells in another unit than it is stocked in has its stock pushed in Sales UOMs (rounded down) and its prices in that unit (`get_sales_units`, ERPNext's `get_conversion_factor` and `get_price_list_rate_for`), as its Sales Order lines have them (ERPNext's selling default). ERPNext has no notion of supplier stock, so backorders and the like are left to other apps: they register a method under the `woocommerce_stock_values` hook (see `apply_stock_value_hooks` and the comment in `hooks.py`) and call `enqueue_stock_update(item_code)` to push again. Keep this app free of company-specific stock rules. Only the **primary** connection (`Item WooCommerce Server.is_primary`, the first row when none is marked, see `get_primary_connection`) updates an existing Item. The other shops only record their sync hash. An Item `validate` hook allows one primary and marks the first row when none is. `sync_sales_orders.py` and `sync_item_prices.py` follow the same pattern.
- The server's **Item Field Map** (`tasks/field_map.py`) copies values of the product into Item fields when an Item is made or force-synced. Each row's JSONPath runs on the product as the doctype has it (`to_dict`, JSON fields decoded), so `validate_item_map` makes it start at one of the doctype's fields (`$.meta_data[?key=='_gtin'].value`, `$.categories[0].name`), and refuses the Item fields the sync owns (`REFUSED_ITEM_FIELDS`). A value the field can't take (a list, a link to a missing record, a number with a decimal comma) is left out and logged once per job (`fit_value`), so a mapping never fails the Item. A row can name a transform, a method another app registers under the `woocommerce_field_transforms` hook (see the comment in `hooks.py`), which changes the value first; the form gets their names from the server's `onload`.
- WordPress keeps names HTML-escaped (`Sleeves &amp; Toploader`): term names always, product names when the user who saved them can't post HTML. The sync takes them as plain text with `unescape_text` (`tasks/sync.py`), which only decodes entities with their semicolon: Item names, attribute options, order line names and mapped values, but not into HTML fields (Text Editor, HTML Editor), where the escaped text reads right. Options are matched to an Item Attribute's values regardless of case, and a variant takes the attribute's spelling: ERPNext refuses two values that differ only in case, and a variant value it doesn't spell exactly.
- Change detection uses a **sync hash**: `Item WooCommerce Server.woocommerce_last_sync_hash` stores the WC `date_modified` from the last sync. Changing how it is written affects loop prevention. It is a Datetime field, so compare it with `get_datetime` on both sides. A product is only pulled when its `date_modified_gmt` (converted to the system timezone) is newer than `Item.modified`, so edits made in ERPNext since aren't overwritten.
- `sync_sales_orders.py` has `SynchroniseSalesOrder`, which pulls WC orders into Sales Orders, built from mixins: `order_status.py` (what a status does, the status push), `order_payment.py` (Sales Invoice and Payment Entry) and `order_lines.py` (lines, taxes and charges).
  - The server's **Order Status Map** (`WooCommerce Server Order Status`, one row per WC status slug) decides what an order means: its `erpnext_action` (skip, submit, submit + invoice, submit + hold, submit + invoice + hold, complete, cancel, close, status only), and which Sales Order status is pushed as that WC status. Defaults are in `DEFAULT_STATUSES`. An action means one thing for an order seen for the first time and another for one that has a Sales Order:
    - Only `CREATING_ACTIONS` create a Sales Order, and with it a Customer, Address and Contact. The Address and Contact come from the order, also for a customer with an account (its addresses can be out of date). A registered customer's Customer is identified by their WooCommerce username (`get_customer_account`, read with the order's own client), or by email when the shop no longer has the account. A guest's is identified by `Guest-{order id}`. Both repeat across shops, so a Customer is looked up within the order's shop (`Customer.woocommerce_server`). The others act on an existing Sales Order only, so a first-seen failed, cancelled or refunded order stays out of ERPNext.
    - Complete SO makes whatever a completed order lacks of its Sales Order, Sales Invoice, Payment Entry and Delivery Note, also when it was completed in WC by mistake, so ERPNext doesn't drift from the shop.
    - Submit SO + Invoice + Hold invoices (and books the payment) before holding, as ERPNext won't invoice a held order. `invoice_and_hold` runs once, when the status is applied, so a hold lifted in ERPNext isn't put back.
    - On an existing Sales Order the hold, resume, cancel and close of an action run once, when the WC status changes. The invoice, payment and delivery steps are idempotent and run on every sync, so pending makes the SI and processing then only adds the PE.
  - **Taxes** are ERPNext's (`tasks/taxes.py`): the server's Sales Taxes and Charges Template taxes every Sales Order, at the rates of each line's Item Tax Template. Its "Is this Tax included in Basic Rate?" tick says whether the rates are the shop's gross prices (ERPNext takes the VAT out, per line) or net; the sync only reads it (`prices_include_tax`) and never converts prices. Items get the template of their product's tax class from the server's Tax Class Map, else `default_item_tax_template`, when created or force-synced. ERPNext can't include tax in an Actual charge, so with an inclusive template the sync splits the VAT out of shipping and fees itself. Shipping is booked on the server's Freight and Forwarding Account, and fees on its Fee Account (else the freight account). Those Actual rows carry `set_by_item_tax_template`, as ERPNext reads a line's VAT rate from the last row on each account.
  - The Sales Invoice and Payment Entry of a Sales Order are found through ERPNext's own links (`get_order_invoices`: Sales Invoice Item.sales_order; `get_order_payment_entries`: Payment Entry Reference), drafts included and cancelled ones not. There are no link fields on the Sales Order. An invoice or payment made by hand counts like one the sync made: the sync makes neither again. A WooCommerce cancel cancels an unpaid invoice that bills only this order, and closes and flags the order otherwise. A cancelled invoice or payment drops out by its docstatus, so the next sync makes a new one.
  - The **Payment Method Map** (`WooCommerce Server Payment Method`) maps a WC gateway id to a Mode of Payment, whose default account for the company is the Payment Entry's account. A method without a row or without a Mode of Payment is never booked; a mapped one is booked once `date_paid` is set.
  - **Pause Order Sync** (`WooCommerce Server.pause_order_sync`, on for a new server) keeps a shop's orders out while its Items are set up: `enqueue_sales_order_sync` and `run_locked` drop them. Unpausing enqueues `sync_paused_orders` for the orders changed since `order_sync_paused_since`. Without that date nothing is enqueued, as it would be the whole shop. The pause doesn't empty the queue: jobs already queued end at once in `run_locked`. Product, price and stock syncs aren't paused.
  - `tasks/item_parity.py` backs the server's **Check Order Items** button: the products of recent orders that no Item is linked to, with an Item suggested by SKU (`find_item_by_sku`), to link (`link_product_to_item`) or create. A link goes through the sync's own `SynchroniseItem.link_item`, so the Item takes the product's prices for the price lists it has none in, and the next price push doesn't end a sale that runs in the shop.
  - `Sales Order.woocommerce_last_sync_hash` is the WC `date_modified` seen at the last pull **or** push. WC is pulled when its `date_modified` is newer (`wc_order_changed`). A push re-reads the order first and pulls instead when WC changed meanwhile, so a payment is never reverted. Never compare with `Sales Order.modified`.
  - Everything for one WC order runs under a file lock (`get_lock_name`), and jobs are enqueued by name with `job_id` + `deduplicate`. `find_sales_order` is the one lookup of a WC order's Sales Order: the newest that isn't cancelled, else the newest cancelled one, so a cancelled order isn't made again. The form syncs through the whitelisted `sync_woocommerce_order` (POST, needs Sales Order create). `run_sales_order_sync` is for code and jobs only.
  - A line whose product the shop no longer has (a 404) gets the placeholder Item, `DELETED_WOOCOMMERCE_PRODUCT`, and the order is flagged instead of failing.
  - A line sold for nothing (a 100% coupon, a free gift) gets a 100% discount (`build_item_row`): ERPNext takes a rate of 0 for one that isn't set and puts the price list rate in its place. Update Items works the discount out itself.
  - Steps the Sales Order doesn't depend on (lines update, invoice, payment) run through `run_flagged`: a failure rolls back to a savepoint and is written to `Sales Order.woocommerce_sync_issue` instead of failing the sync. Totals that differ from WC are flagged too, which blocks auto-invoicing.
- Documents created or updated by the sync set `doc.flags.created_by_sync` so the doc-event hooks don't re-trigger a sync. `WooCommerce Order.on_update` has the guard too, as a status push saves the order. Keep that guard on any new hook. A pull writes the Sales Order's own WooCommerce fields with `db_set` rather than a save, so it is not validated again and gets no Version on every pull.
- The sync entry points are:
  - `doc_events` in [hooks.py](woocommerce_conduit/hooks.py): `Sales Order` on_submit (order sync) and on_change (status push, which also sees the status changes ERPNext makes with `db_set`), `Item Price` on_update (price push), `Stock Ledger Entry` on_submit (stock push: ERPNext submits one for every stock movement and one for its reversal, whichever doctype makes it) and `Sales Order` submit/cancel (reserved stock, only where a server subtracts it). Each enqueues a job after commit. The stock hooks collect the Items of a transaction (`enqueue_stock_updates`) and push each Item linked to WooCommerce once. A price or stock job is skipped while one for the same Item is still waiting in the queue (`enqueue_unless_queued` in `tasks/sync.py`), but not while one runs, as that one may have read the old values. There is no Item hook, as Item changes don't go to WooCommerce. There is no queue or batching layer yet. Pushes are shaped for one: a push computes the values, compares them with the product (`get_changes`) and writes only the differences (`write`).
  - Jobs get names (`item_code`, `woocommerce_product_name`), never documents, and load the product themselves.
  - Scheduler: `hourly_long` (orders modified since the last sync, leaving out those whose Sales Order has seen the change already, as the webhook usually got there first; the cursor is stored in `WooCommerce Settings` with `set_single_value`; products are pulled through the orders) and `daily_long` (full price and stock push, as a safety net, in jobs of 100 Items). `sync_woocommerce_products_modified_since` is no longer scheduled; run it by hand for a bulk import.
  - Webhook: `order_created` in [endpoint.py](woocommerce_conduit/endpoint.py) takes both the "Order created" and "Order updated" webhooks. It is guest-whitelisted and validated by an HMAC-SHA256 signature against the server's `secret`, compared in constant time. Only then does it run as the server's `creation_user`. WooCommerce's ping (`webhook_id=…`, sent unsigned when a webhook is saved) gets a 200 and does nothing. A webhook of a disabled server is acknowledged and ignored.

### Config doctypes

`WooCommerce Server` holds credentials (consumer key/secret are Password fields), the webhook secret, and mapping child tables (item fields, order statuses, payment methods, shipping rules). Call the shop from the server form with `get_api()`: it adds the URL scheme and reads the stored password when the form sends it masked, so it works before the server is saved. The "Add Missing ..." buttons get `{"rows", "error"}` from `fetch_names`. `Item WooCommerce Server` is a child table on `Item` (added via `fixtures/custom_field.json`) that links an Item to its WC ID per server. `WooCommerce Settings` is a Single doctype for global sync options.

## Gotchas

- Patches live in `patches/v1/` and are listed in `patches.txt`. Add one there for data migrations, not an inline `migrate` hack. A fixture removed from `hooks.py` stays on existing sites until a patch deletes it.
- Doctype Python files have an auto-generated `DF` types block. Don't hand-edit inside it. It regenerates from the JSON on `bench migrate` in developer mode, or without it: `TypeExporter(frappe.get_doc("DocType", name)).export_types()` from `frappe.types.exporter` in `bench console`.
- A doctype test module makes the test records of every doctype its doctype links to, which clashes with ERPNext's (duplicate "Standard Buying"). Tests that only build docs in memory set `IGNORE_TEST_RECORD_DEPENDENCIES`.
- Whitelisted methods check argument types against their annotations in tests too, so pass ids as `str` where the signature says `str`.
- ERPNext's `update_child_qty_rate` (Update Items) takes a row sent without a description for a changed row and empties its description, so `update_sales_order_items` sends each row's own.
