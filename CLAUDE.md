# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Frappe/ERPNext app (`woocommerce_conduit`, requires `erpnext`) that syncs WooCommerce items, item prices and orders with ERPNext. It is a slimmer rewrite related to the `woocommerce_fusion` app that sits beside it in `apps/`. Fusion has features Conduit does not: a sync queue, field transforms, two-way Item sync. Conduit's stock sync (`tasks/stock_update.py`) and Item form buttons (`public/js/item.js`) are ported from Fusion. Do not assume Fusion code can be copied as-is, because the sync classes differ.

The repo root is the app dir; the Python package is the nested `woocommerce_conduit/` folder. The Frappe module is `woocommerce_conduit/woocommerce/`, which holds all doctypes.

Lint/format (run in the app dir): `pre-commit run --all-files`. It uses ruff (lint, including the pyupgrade rules, import sort and format), eslint and prettier. pre-commit only checks files git tracks, so `git add` new files first.

- The lint tools follow Frappe core's own `.pre-commit-config.yaml` and the `bench new-app` template of the installed Frappe (`frappe/utils/boilerplate.py`): pre-commit-hooks 6.0.0, ruff 0.14.10, prettier 2.7.1, eslint 8.44.0. The `[tool.ruff]` ignore list follows the template too. Bump them when Frappe does, and never ahead of it, so the app formats and lints like Frappe.

- CI (`.github/workflows/ci.yml`) installs the app on a fresh bench of the pinned Frappe and ERPNext versions (`TEST_AGAINST_FRAPPE_VERSION`, `TEST_AGAINST_ERPNEXT_VERSION`; Python 3.14, Node 24) and runs `run-tests --app woocommerce_conduit`. `linter.yml` runs Frappe Semgrep rules and pip-audit.

## Architecture

### Virtual doctypes backed by the WooCommerce REST API

`WooCommerce Product` and `WooCommerce Order` are **virtual doctypes**. They have no DB tables. They subclass `WooCommerceDocument` in [woocommerce/woocommerce_api.py](woocommerce_conduit/woocommerce/woocommerce_api.py), which implements `load_from_db`, `get_list_of_records`, `get_count_of_records` and `db_update`. `db_insert`/`delete` are no-ops.

- `db_update` PUTs only the fields that differ from `_doc_before_save` (which `save()` re-fetches from WooCommerce), filtered and shaped by the subclass's `before_db_update`, and stores the returned `date_modified`. `write(changes)` sends changes without the reload `save()` does. For many records, `load_records` reads them by id, 100 a request (`include`), with only the fields asked for and without `after_load_from_db`, and `write_batch` sends up to 100 updates in one POST to a batch endpoint (`get_batch_endpoint`: `products/batch`, or `products/{parent}/variations/batch` for a variation). It sends no `_fields`, which WordPress would apply to the answer's `update` key and so drop the records. The price and stock pushes compare with the record they just loaded (`get_changes`) and only write what differs, because WooCommerce dates every save as a change and fires its product-updated hooks. `WooCommerce Product` only ever writes the price and stock fields in `writable_fields`. `WooCommerce Order` only writes `status`. Frappe's length/select validators are disabled on these doctypes, because WooCommerce decides what is valid.
- A record's `name` is `"{server_domain}~{wc_id}"` (`WC_RESOURCE_DELIMITER = "~"`). Use `generate_woocommerce_record_name_from_domain_and_id` and `get_domain_and_id_from_woocommerce_record_name` rather than building or parsing it by hand.
- `WooCommerceDocument.__init__` takes the `WooCommerceAPI` clients of the **enabled** servers from `get_api_clients`, and throws `SyncDisabledError` if none exist. The clients are built once per request or job (`request_cache`, cleared when a server is saved), as each needs the server's passwords decrypted.
- WooCommerce orders each server's records: by the list's first sort field when it can (`orderby_map` and `COMMON_ORDERBY_MAP`, which has Last Updated for products and orders alike), else by date, newest first, which is then asked for explicitly. An ordered list of several servers is merged in that order: each server is read from its first record to the end of the page, and the merged records are cut to the page (`_get_merged_records`), so page n reads n pages of every server. An unordered list, or one of a single server, reads the servers one after the other, as one list (`_get_records_in_turn`): a server whose records all lie before the offset is skipped by its `x-wp-total`, and no server is asked once the page is full. The syncs read that way, as they don't order. The page is then ordered as asked (`sort_records`: a name orders by its id as a number, text regardless of case). Only Frappe's list and report views send an order and a `start`. `page_length` is how many records to return, fetched `per_page` (at most 100) a request. `servers` limits the servers read.
- `load_from_db` raises `frappe.DoesNotExistError` on a 404 whose error code says the id is invalid (`is_invalid_id`: `woocommerce_rest_shop_order_invalid_id` and the like), which isn't logged as an error. Any other 404, say of a shop whose REST API is off, is an error, as an order taken for deleted has its Sales Order cancelled.
- Filters are normalised with Frappe's `Filters`, so a dict or lists of 3 or 4 all work (`map_frappe_filters_to_wc_params`). A `woocommerce_server` filter, or one on record names, picks the servers to read (`get_servers_from_filters`). `name`/`id` become `include`, and the date fields become after/before (`Between` covers whole days). Any other filter is an error, as dropping it would return unrelated records. `get_count` uses the same filters.
- Each subclass declares `resource`, `field_setter_map`, `field_getter_map` (Frappe fieldname → WC fields it needs), `orderby_map` and `mandatory_wc_fields`. Only the WC fields needed for the requested Frappe fields are requested (`_fields`). When you add a field to a virtual doctype, update these maps so it is actually fetched.
- `WooCommerceAPI` wraps the `woocommerce` client of one server. A request that the shop answers with a 429 or a 5xx, or whose connection drops, is sent again up to 3 times, after 1, 2 and 4 seconds (a little longer at random) or the shop's `Retry-After` when longer, while the next try can start within 2 minutes of the first, or 10 seconds in a web request (`get_retry_delay`). A POST is only sent again after a 429, as after a 5xx the shop may have made the record, unless it is `idempotent`: a batch of updates only sets values, so it is sent again like a PUT. Timeouts and SSL errors aren't retried. The loop is around `super()._API__request`, so the client signs each try anew. Its failed requests, every retried try among them, and all of them when the server has `log_all_requests` ticked, are kept as Frappe **Integration Requests** (service "WooCommerce", linked to the server). They are written through `frappe.deferred_insert`, so a rolled-back sync keeps its log. They show up within 15 minutes, and Log Settings clears them after 90 days. Nothing is logged under `frappe.in_test`.
- Complex values (dicts/lists) are JSON-serialised into JSON fields. `after_load_from_db` on each subclass prettifies them for the form. What a sync needs goes in `pre_init_document` instead, which every record goes through, a list's too: WooCommerce Product's `dimensions` become its `length`, `width` and `height` there, so the Item Field Map finds them on the records of `load_records`.
- `WooCommerce Product.get_list` also fetches variations. Its behaviour (variation fetching, batch size, max variations) is driven by `WooCommerce Settings`. Lists are never cached, so they show what WooCommerce has now.

### Sync layer (`tasks/`)

- Each sync is a class of its own (`SynchroniseItem`, `SynchroniseSalesOrder`, `SynchroniseItemPrice`), with no shared base class. Each loads the servers it needs with `get_cached_doc`. `tasks/sync.py` has `record_sync_time`.
- `sync_items.py` has `SynchroniseItem`, which syncs WC products **into** ERPNext Items, one way. A product is pulled **once**: a missing Item is created (with its regular and sale price as Item Prices) when an order needs it, on a manual sync or by Import Products, and a linked Item is only updated again with `force_update` (the Sync buttons). On a server that names Items by SKU, a product is linked instead to the enabled Item whose code or barcode is its SKU (`find_item_by_sku`, a template only for a variable product). That Item keeps its fields and takes the product's prices only for the price lists it has none in (`link_item`). A made or linked Item gets the default warehouse of the server's company in its Item Defaults, unless it has one for that company (`set_default_warehouse`): ERPNext 16 moved the default warehouse to the Company, but a new Item still looks for the global one Stock Settings had, so it gets none. It runs after the insert or save, as ERPNext gives an Item without defaults those of its Item Group. A code that is taken gets a number (`append_number_if_name_exists`), as ids repeat across shops. One Item can be linked to several shops, and each shop keeps its own name, description, etc., so Item fields are never written back to WooCommerce. Only prices (`sync_item_prices.py`) and stock (`stock_update.py`) go from ERPNext to WooCommerce, each switched per `WooCommerce Server` (`enable_price_list_sync`, `enable_stock_level_synchronisation`) and per Item connection (`Item WooCommerce Server.enable_sync`, "Sync Prices and Stock", default on). Stock is the sum of the server's `warehouses`, a group counting with the warehouses under it (ERPNext's `get_child_warehouses`). The regular price is the Item Price ERPNext would charge today (`get_item_prices_for_stock_uom`: valid today, in the stock UOM, for anyone). The sale is the running one that started last, else the next one to start, which WooCommerce schedules (`pick_sale`). With the server's `sync_in_sales_uom`, an Item that sells in another unit than it is stocked in has its stock pushed in Sales UOMs (rounded down) and its prices in that unit (`get_sales_units`, ERPNext's `get_conversion_factor` and `get_price_list_rate_for`), as its Sales Order lines have them (ERPNext's selling default). ERPNext has no notion of supplier stock, so backorders and the like are left to other apps: they register a method under the `woocommerce_stock_values` hook (see `apply_stock_value_hooks` and the comment in `hooks.py`) and call `enqueue_stock_update(item_code)` to push again. Keep this app free of company-specific stock rules. Only the **primary** connection (`Item WooCommerce Server.is_primary`, the first row when none is marked, see `get_primary_connection`) updates an existing Item. The other shops only record their sync hash. An Item `validate` hook allows one primary and marks the first row when none is. `sync_sales_orders.py` and `sync_item_prices.py` follow the same pattern.
- The server's **Item Field Map** (`tasks/field_map.py`) copies values of the product into Item fields when an Item is made or force-synced. Each row's JSONPath runs on the product as the doctype has it (`to_dict`, JSON fields decoded), so `validate_item_map` makes it start at one of the doctype's fields (`$.meta_data[?key=='_gtin'].value`, `$.categories[0].name`), and refuses the Item fields the sync owns (`REFUSED_ITEM_FIELDS`). A value the field can't take (a list, a link to a missing record, a number with a decimal comma) is left out and logged once per job (`fit_value`), so a mapping never fails the Item. A row can name a transform, a method another app registers under the `woocommerce_field_transforms` hook (see the comment in `hooks.py`), which changes the value first; the form gets their names from the server's `onload`. A mapped value is compared with what the Item keeps as the Item's save would store it (`as_saved`, see Gotchas), so an unchanged product doesn't re-save the Item.
  - **Update Linked Items** on the server form (`tasks/linked_item_update.py`) applies the map to the Items linked already, which nothing does on its own. A person picks the map rows, and a background job (`review_linked_items`, on `long`, once per shop and person) reads the products of the Items whose primary connection is the shop, through `load_products` with only the fields the rows' paths start at (every field when a row has a transform, which gets the record) and each variation on its own at `products/{id}`, as the sync reads it. What each Item would get is kept for that person in the cache for 6 hours (`keep_review`), each Item in a hash under its code, so an update reads and drops only the Items it saves, with an id the form sends back, so a newer review never stands in for the one shown. The form lists it as old → new (`get_linked_item_review`), nothing ticked. Only the ticked Items are saved, 50 a request (`update_linked_items`), each in a savepoint, after checking it is still linked to the product and has the values it was reviewed with; done Items leave the review, failed ones stay to be tried again.
  - A template follows its variants, as some families are made in ERPNext with each variant linked to its product by its own id and the template linked to nothing: for each field all its enabled variants would have the same, non-empty value in, the template gets that value rather than its own product's (`add_template_changes`). Its row ticks itself when every variant whose value it waits for is ticked, and it is saved after them, only if they all have the value by then. These saves set `dont_update_variants`, so a variant changes only when it is ticked itself.
- WordPress keeps names HTML-escaped (`Sleeves &amp; Toploader`): term names always, product names when the user who saved them can't post HTML. The sync takes them as plain text with `unescape_text` (`tasks/sync.py`), which only decodes entities with their semicolon: Item names, attribute options, order line names and mapped values, but not into HTML fields (Text Editor, HTML Editor), where the escaped text reads right. Options are matched to an Item Attribute's values regardless of case, and a variant takes the attribute's spelling: ERPNext refuses two values that differ only in case, and a variant value it doesn't spell exactly.
- Change detection uses a **sync hash**: `Item WooCommerce Server.woocommerce_last_sync_hash` stores the WC `date_modified` from the last sync. Changing how it is written affects loop prevention. It is a Datetime field, so compare it with `get_datetime` on both sides. A product is only pulled when its `date_modified_gmt` (converted to the system timezone) is newer than `Item.modified`, so edits made in ERPNext since aren't overwritten.
- `sync_sales_orders.py` has `SynchroniseSalesOrder`, which pulls WC orders into Sales Orders, built from mixins: `order_status.py` (what a status does, the status push, and the invoices and payments people made for a Sales Order), `order_lines.py` (lines, taxes and charges) and `order_customer.py` (the Customer, Address and Contact of a new Sales Order). It makes and keeps Sales Orders only: an invoice is made only when its payment is processed, so people invoice, pay and deliver a regular order in ERPNext, and a WooCommerce Order Import does it for the orders ERPNext first meets completed (see below).
  - The server's **Order Status Map** (`WooCommerce Server Order Status`, one row per WC status slug) decides what an order means: the actions its row ticks, a Check each (`ACTIONS`: submit, hold, cancel, close, skip; `get_actions()` gives them as a frozenset, none for a status the map doesn't know), and which Sales Order status is pushed as that WC status. Defaults are in `DEFAULT_STATUSES`. Cancel, close and skip are ticked alone (`validate_status_actions`; the form unticks them as well). A status with a row that ticks none of cancel, close and skip is active (`is_active_status`). With nothing ticked, an existing Sales Order only takes the order's status and lines, and a hold put on it is lifted. Skip leaves the order alone, and its status out of the hourly sync. An action means one thing for an order seen for the first time and another for one that has a Sales Order:
    - Only submit creates a Sales Order, and with it a Customer, Address and Contact (see the Customer below). The others act on an existing Sales Order only, so a first-seen failed, cancelled or refunded order stays out of ERPNext. Completed ticks nothing by default, so an order first seen completed is left to a WooCommerce Order Import, which books its payment (`untick_submit_on_completed` unticked the old default).
    - On an existing Sales Order the hold, cancel and close run once, when the WC status changes, and so does the lifting of a hold, which every active status without hold does, completed among them.
    - An order the shop deleted for good (`load_wc_order` raises `DoesNotExistError`, and the sync sets `deleted_in_woocommerce`) is taken for one in the trash, which it usually went through: `sync_deleted_order` sets `woocommerce_status` to `trash` and applies what the `trash` row ticks, once, also when a status push finds it gone. A Sales Order whose order is in the trash isn't pushed to, as a status would take the order out of it.
    - An order that comes back (`came_back`: its status is active, and the one its Sales Order last saw ticks cancel or close), say restored from the trash or paid on a retry after it failed, gets its Sales Order back, also when it is back as completed, which makes no Sales Order and which an import leaves out, as it has one. A cancelled one is amended (`amend_sales_order`, like the form's Amend, which copies every field) and the pull carries on with the amendment; the sync only cancels a Sales Order nothing was paid on or delivered. A closed one is reopened and flagged (`reopen_sales_order`). A Sales Order cancelled or closed in ERPNext while the shop went on with the order is left alone.
  - **Taxes** are ERPNext's (`tasks/taxes.py`): the server's Sales Taxes and Charges Template taxes every Sales Order, at the rates of each line's Item Tax Template. Its "Is this Tax included in Basic Rate?" tick says whether the rates are the shop's gross prices (ERPNext takes the VAT out, per line) or net; the sync only reads it (`prices_include_tax`) and never converts prices. Items get the template of their product's tax class from the server's Tax Class Map, else `default_item_tax_template`, when created or force-synced. ERPNext can't include tax in an Actual charge, so with an inclusive template the sync splits the VAT out of shipping and fees itself, unless WooCommerce taxed the order (it has `tax_lines`) and not that charge: the shop left it untaxed, so it is booked whole. Shipping is booked on the server's Freight and Forwarding Account, and fees on its Fee Account (else the freight account). A Shipping Rule charges the shipping itself, without VAT, so the sync then books only the VAT the shop charged on it (`with_shipping` off in `build_charges`). Those Actual rows carry `set_by_item_tax_template`, as ERPNext reads a line's VAT rate from the last row on each account.
  - The Sales Invoices and Payment Entries of a Sales Order, which people make, are found through ERPNext's own links (`get_order_invoices`: Sales Invoice Item.sales_order; `get_order_payment_entries`: Payment Entry Reference), drafts included and cancelled ones not. There are no link fields on the Sales Order. The sync never cancels or deletes one: a WooCommerce cancel cancels a Sales Order nothing was invoiced, paid or delivered on, and closes and flags it otherwise. A closed one stays closed, as ERPNext won't cancel it, nor one that a draft invoice bills. A Sales Order reaches Completed, and its status is pushed, only once a person has invoiced and delivered it.
  - A **WooCommerce Order Import** (`tasks/order_import.py`, one document per import, `WC-ORD-IMP-#####`) brings in the completed orders of a shop that have no Sales Order (`get_orders_to_import`: `status = completed` in its date range, by id, leaving out the ids that have a Sales Order of any docstatus): the old ones, and those completed while the sync wasn't watching. Start Import counts them first (`count_orders_to_import`, which lists them as the job does, through `list_orders_to_import`, with the payment fields), and its confirm names the payment methods whose orders it would skip, with their ids, those missing from the map included; a count that fails (the shop can't be read) is said, and the import can still start. `start_order_import` checks the permissions of everything the job makes, as it runs as the user, and enqueues `import_orders` once per shop (`get_import_job_id`). The job commits each order, rolls back a failed one, and logs each in a `WooCommerce Order Import Log` row (Paid, Needs Review, Skipped, Failed; a rerun replaces the Skipped and Failed rows of an order), then counts them, also after a timeout (`JobTimeoutException` is re-raised, not caught). `frappe.flags.woocommerce_order_import` holds off the status push meanwhile, as ERPNext changes an imported Sales Order's status on a copy of its own, without `created_by_sync`.
    - `OrderImport`, a `SynchroniseSalesOrder`, runs under the order's lock, also while the order sync is paused (`run_locked(..., while_paused=True)`). An order with something to pay whose payment method has no Mode of Payment in the import's **Payment Method Map** (`WooCommerce Order Import Payment Method`, `get_booking_row`), or whose Mode of Payment has no account for the company, is skipped with nothing made, so a later run imports it whole. Otherwise it gets its Sales Order as the sync makes one (`create_sales_order(frozenset())`), then its invoice and Payment Entry, both submitted (`make_invoice`, `make_payment_entry`) and dated at the moment the map row of its payment method picks (`get_paid_at`, the row's Payment Date): `date_paid`, or `date_completed` for money that comes in later than WooCommerce's paid date, as WooCommerce takes cash on delivery as paid at checkout, and a reserved product may be paid by transfer once it is in stock. That is, unless a person must decide (Needs Review, flagged on the Sales Order): it was flagged when it was made, or has no such date, or `refunds`, or nothing to pay. The invoice's due date is worked out for its posting date, as the mapper took today's, which a Payment Terms Template refuses. The Payment Entry takes the row's Bank Account, or none, never the company default that `get_payment_entry` puts there, and validate makes a row's Bank Account the company's, on its Mode of Payment's account. Any error fails the whole order, its Customer and Items included, so a missing Fiscal Year or a delivery without stock is tried again by the next run.
    - With Make Delivery Notes, the order is delivered dated at its completion, with its serial numbers. Without it, or when it isn't fully delivered, the Sales Order is reloaded (its invoice changed it) and closed, and its Stock Reservation Entries cancelled, so it reserves no stock. A person re-opens it to invoice it by hand.
    - **Serial numbers** come from a CSV attached to the import, strictly `order_number,serial_no` (`tasks/order_import_serials.py`, `parse_serial_file`). `check_serial_numbers` runs on save and at the start, leaves out the rows of imported orders (by `po_no`), and refuses the whole file, listing every row, unless each serial is Active in the server's `warehouse`, which order lines ship from, of its company. `assign_serial_numbers` hands an order's serials out over its serialized lines into their `serial_no`, from which ERPNext 16 makes the Serial and Batch Bundle, marks them Delivered to the Customer and dates their warranty from the delivery. A count that doesn't match, a serial of an Item not on the order, or one that came into stock (`Serial No.posting_date`) after the completion fails the order. Batch Items aren't handled. `public/order_import/serial_numbers_guide.md` tells an LLM how to write the script that converts a company's earlier records into the schema.
  - The **Shipping Method Map** (`WooCommerce Server Shipping Rule`, the switch `enabled_shipping_methods`) gives a new Sales Order the Shipping Rule of its order's first shipping line (`get_shipping_rule`). A row names a method of a shipping zone as WooCommerce does, `method_id:instance_id` (`get_shipping_method_key`), so two flat rates can get different rules. A bare `method_id` row is for every method of that kind without a rule of its own. A row without a rule is charged as WooCommerce charged it. ERPNext works the charge out from the rule, so the rules have to give the shop's shipping net of VAT, or the totals check flags the order. `validate_shipping_rule_map` refuses a rule a Sales Order of the company can't take: not for selling, of another company, disabled, or on the account fees are booked on (ERPNext puts the rule's charge on the last Actual row of its account, which would be a fee).
  - **The Customer** of a new Sales Order (`SalesOrderCustomerMixin`) is looked up within the order's shop (`Customer.woocommerce_server`), as ids and usernames repeat across shops. It is the Customer with the order's tax ID (from the Customer Field Map, compared by `normalise_tax_id`, so `PL 679-100-38-01` is `6791003801`); else a registered customer's, by their WooCommerce username (`get_customer_account`, read with the order's own client), or by email when the shop no longer has the account, or the Customer theirs was merged into (`get_merged_customer`, see Possible duplicates); else, for a guest or an account whose `role` is in `STAFF_ROLES` (administrator, shop_manager: they place orders for other people), the one with a Contact holding the billing email. The email and tax ID lookups pass over disabled Customers. An order with a tax ID takes the account's or email's Customer only when it has no tax ID and the order's name, and then fills it in; otherwise a Customer is made for the tax ID, identified as `TaxID-{normalised}` when the username names the other one. A new Customer is identified by the username, else by `Guest-{order id}`.
    - ERPNext fetches `customer_name` and `tax_id` from the Customer onto every Sales Order, invoice and delivery, and renders their address text from the linked Address whenever they are saved (`SellingController.set_customer_address`), and DHL24 names the receiver after the Customer. So an order never renames the Customer it finds or edits an Address. It only fills what the Customer lacks (a tax ID as above, empty mapped fields, a primary Address or Contact), takes the Customer's Address with the same lines, city, state, postcode, country and phone (`get_address_key`, regardless of case and spaces) or adds one titled with the name the order gives it, and takes the Contact with the billing email and name or adds one. A shipping address the order leaves empty is the billing one, and one without a phone has the billing phone. The Sales Order links them (`set_customer_in_sales_order`, contact fields included), as ERPNext would otherwise give it the Customer's defaults, another order's.
    - A Customer found by account or email that bears another name than the order (its company, else its person) may not be the buyer, say a typo or someone else on the same email: the Sales Order is flagged (`customer_issues`, written to `woocommerce_sync_issue` before the submit), which an Order Import leaves without an invoice. A tax ID match isn't checked, as the tax ID says which company it is.
  - **Possible duplicates** (`tasks/customer_duplicates.py`, `public/js/customer.js`): Customers are never merged without a person. A Customer's form lists, in its Possible Duplicates field (an HTML custom field in a full-width section at the top of the form, above the shop's fields, shown by its `depends_on` only when there are some), the enabled Customers whose Contacts share an email or a phone (`normalise_phone`, the last 9 digits) with it, or that have its tax ID, worked out by the Customer `onload` hook. A name alone is left to the WooCommerce Duplicate Customers report, which groups every Customer, also those made by hand, by email, tax ID, phone, email domain or name. It leaves out the domains of WooCommerce Settings' Ignore Email Domains (free mail providers, which say nothing about who the customer is). Review shows the two side by side, and the person merges them, with Frappe's own merge (`merge_customers` is `frappe.rename_doc(..., merge=True)`, as Rename is in the desk), or marks them Not the Same.
    - What was decided is a **WooCommerce Customer Decision**: Not the Same (`customer`, `other_customer`), which the form and the report then leave out, or Merged (`customer` is the kept one, with the merged Customer's former ID, shop and identifier as text). Frappe's merge moves every Link to the Customer it removes, so the decisions follow any merge, also one made with Rename.
    - The Customer hooks handle every merge, however it was started. `before_rename` remembers the kept Customer's name, and `after_rename` (`record_merge`, while the merged Customer still exists) puts it back, gives the kept one what it lacks (the tax ID; the shop and identifier when it was made by hand), records the Merged decision and drops the Not the Same pair that now names the Customer twice. The order sync finds the kept Customer by a merged account's identifier (`get_merged_customer`), so its next order doesn't make a new one.
  - The **Customer Field Map** (`WooCommerce Server Customer Field`) copies values of the order into its Customer: a plugin's checkout field kept in the order's `meta_data`, say a tax ID (`$.meta_data[?key=='_billing_nip'].value`). It goes through `tasks/field_map.py` like the other maps. Its paths run on the order as the WooCommerce Order doctype has it (`get_order_data`: its fields, JSON decoded, `meta_data` included), so `validate_customer_map` makes them start at one of its fields. It may only write Customer's custom fields (not the sync's own) and `tax_id` (`get_customer_map_fields`). A new Customer gets every value, a Customer the order finds only those it has none of, and none when it is flagged.
  - The **Order Line Fields** map (`WooCommerce Server Order Item Field`) copies values of an order line, as WooCommerce sends it in `line_items`, into its Sales Order Item when the row is made: on a new Sales Order (`build_item_rows`) and on the rows Update Items adds (`link_new_rows`, which writes without a save and so sanitises the values itself). It goes through `tasks/field_map.py` like the Item Field Map, but may only write Sales Order Item's custom fields (not the sync's own) and `item_name`, `description` and `additional_notes` (`get_order_item_map_fields`): every other field changes what the line costs, how it is taxed or delivered. Its paths aren't checked against the line's fields, as plugins add their own.
  - **Pause Order Sync** (`WooCommerce Server.pause_order_sync`, on for a new server) keeps a shop's orders out while its Items are set up: `enqueue_sales_order_sync` and `run_locked` drop them. Unpausing enqueues `sync_paused_orders` for the orders changed since `order_sync_paused_since`. Without that date nothing is enqueued, as it would be the whole shop. The pause doesn't empty the queue: jobs already queued end at once in `run_locked`. Product, price and stock syncs aren't paused.
  - `tasks/item_parity.py` backs the server's **Check Order Items** button: the products of recent orders that no Item is linked to, with an Item suggested by SKU (`find_item_by_sku`), to link (`link_product_to_item`) or create. A link goes through the sync's own `SynchroniseItem.link_item`, so the Item takes the product's prices for the price lists it has none in, and the next price push doesn't end a sale that runs in the shop.
  - `Sales Order.woocommerce_last_sync_hash` is the WC `date_modified` seen at the last pull **or** push. WC is pulled when its `date_modified` is newer (`wc_order_changed`). A push re-reads the order first and pulls instead when WC changed meanwhile, so a payment is never reverted. Never compare with `Sales Order.modified`.
  - Everything for one WC order runs under a file lock (`get_lock_name`), and jobs are enqueued by name with `job_id` + `deduplicate`. `find_sales_order` is the one lookup of a WC order's Sales Order: the newest that isn't cancelled, else the newest cancelled one, so a cancelled order isn't made again. The Sales Order's WooCommerce fields are no-copy (`custom_fields.py`), so a Duplicate, or an Auto Repeat, is a Sales Order of no order, which the sync never syncs nor finds, while an amendment stays the order's, as Amend copies no-copy fields (the form's `from_amend`, and `frappe.copy_doc` in `amend_sales_order`). The form syncs through the whitelisted `sync_woocommerce_order` (POST, needs Sales Order create). `run_sales_order_sync` is for code and jobs only.
  - A new Sales Order gets ERPNext's naming series, and the order's number (`number`, else its id) goes in `po_no`. A server with `name_sales_orders_by_number` names it by its `sales_order_prefix` and that number instead (`get_sales_order_name`, passed to `insert(set_name=…)`). A naming series always ends in a counter, and a Document Naming Rule in its own, while a hook or a Sales Order class would name the Sales Orders made by hand too and could clash with other apps. A name that is taken (by another shop's order, or a Sales Order made by hand) falls back to the naming series without a flag, as a flag would hold back an Order Import's invoice. `validate_sales_order_prefix` keeps the servers' prefixes apart. Frappe names an amendment `{name}-1`.
  - A line whose product the shop no longer has (a 404) gets the placeholder Item, `DELETED_WOOCOMMERCE_PRODUCT`, and the order is flagged instead of failing.
  - A line sold for nothing (a 100% coupon, a free gift) gets a 100% discount (`build_item_row`): ERPNext takes a rate of 0 for one that isn't set and puts the price list rate in its place. Update Items works the discount out itself.
  - Steps the Sales Order doesn't depend on (the lines update) run through `run_flagged`: a failure rolls back to a savepoint and is written to `Sales Order.woocommerce_sync_issue` instead of failing the sync. Totals that differ from WC are flagged too, which holds back an Order Import's invoice.
- Documents created or updated by the sync set `doc.flags.created_by_sync` so the doc-event hooks don't re-trigger a sync. `WooCommerce Order.on_update` has the guard too, as a status push saves the order. Keep that guard on any new hook. A pull writes the Sales Order's own WooCommerce fields with `db_set` rather than a save, so it is not validated again and gets no Version on every pull.
- The sync entry points are:
  - `doc_events` in [hooks.py](woocommerce_conduit/hooks.py): `Sales Order` on_submit (order sync) and on_change (status push, which also sees the status changes ERPNext makes with `db_set`), `Item Price` on_update (price push), `Stock Ledger Entry` on_submit (stock push: ERPNext submits one for every stock movement and one for its reversal, whichever doctype makes it) and `Sales Order` submit/cancel (reserved stock, only where a server subtracts it). Each enqueues a job after commit. The stock hooks collect the Items of a transaction (`enqueue_stock_updates`) and push each Item linked to WooCommerce once, in a job of its own, or 100 a job through the daily push's batch path (`enqueue_batch_pushes`) when the transaction moves more than `MAX_ITEMS_PUSHED_ALONE` (10) linked Items, so a Stock Reconciliation of 500 Items makes 5 jobs rather than 500. Those jobs go on the `default` queue of the single pushes, not behind the order syncs of `long`. A price or stock job of one Item is skipped while one for the same Item is still waiting in the queue (`enqueue_unless_queued` in `tasks/sync.py`), but not while one runs, as that one may have read the old values. There is no Item hook, as Item changes don't go to WooCommerce. There is no queue. A push computes the values, compares them with the product (`get_changes`) and writes only the differences. One Item (the hooks, the Item form buttons) is pushed product by product: `load_from_db`, then `write`. The daily jobs push in batches through `push_to_products` (`tasks/product_push.py`):
    - A server's products are read 100 a request with only `writable_fields`. A variation is read with the others of its parent, which ERPNext knows from its Item's template (`get_variation_parents`). A product its list leaves out (a variation whose Item isn't a variant, a trashed or deleted product) is read on its own.
    - The changes go 100 a request to the batch endpoints. A product WooCommerce refuses, or a request that fails, is logged, and the others go on. `price_list_delay_per_item` waits for each product written, also in a batch.
    - Single Items keep their own path, so a fault in the batch path can't stop the pushes that keep the shop right during the day.
  - Jobs get names (`item_code`, `woocommerce_product_name`), never documents, and load the product themselves.
  - Scheduler: `hourly_long` (orders modified since the last sync, leaving out those whose Sales Order has seen the change already, as the webhook usually got there first; the cursor is stored in `WooCommerce Settings` with `set_single_value`; products are pulled through the orders). The completed ones it lists without a Sales Order wait for an import, as the sync makes none for them, so the enabled System Managers, Administrator included, get one bell notification per shop and run naming them (`notify_orders_to_import`, an `Alert`, which Frappe sends by no email), linked to the shop's imports. A paused shop is left out until `sync_paused_orders` lists its orders, and so is a shop whose `completed` row ticks Submit. A notice that fails is logged and doesn't stop the sync and `daily_long` (full price and stock push, as a safety net, in jobs of 100 Items). Products aren't pulled on a schedule.
  - **Import Products** on the server form (`start_product_import`) enqueues `import_products` for its shop (on `long`, `job_id` + `deduplicate`, so once at a time; `enqueue_product_import` from bench). It lists the shop's published products and their published variations by id, leaves out those linked already and the grouped and external ones (`get_products_to_import`), and syncs them one after the other, so a variation never makes its parent's Item while the parent's own sync does. The products are read 100 a request with every field (`read_products`, through `load_records`), the variations one by one, as a variation's record at its parent's endpoint isn't the one `products/{id}` gives, which the sync reads. Each product is committed when made (a manual commit, as Data Import does), and a failure rolled back and counted (it is logged where it happened), and the progress sent to the server's form (`publish_import_progress`, the `woocommerce_product_import` event, shown with `frm.dashboard.show_progress`). It holds a long-queue worker while it runs; one that stops is carried on by starting it again.
  - Webhook: `order_created` in [endpoint.py](woocommerce_conduit/endpoint.py) takes the "Order created", "Order updated", "Order deleted" and "Order restored" webhooks (`ORDER_EVENTS`); a deleted order comes as its id alone. It is guest-whitelisted and validated by an HMAC-SHA256 signature against the server's `secret`, compared in constant time. Only then does it run as the server's `creation_user`. WooCommerce's ping (`webhook_id=…`, sent unsigned when a webhook is saved) gets a 200 and does nothing. A webhook of a disabled server is acknowledged and ignored.

### Config doctypes

`WooCommerce Server` holds credentials (consumer key/secret are Password fields), the webhook secret, and mapping child tables (item fields, order statuses, shipping rules, order line fields, customer fields). Call the shop from the server form with `get_api()`: it adds the URL scheme and reads the stored password when the form sends it masked, so it works before the server is saved. The "Add Missing ..." buttons get `{"rows", "error"}` from `fetch_names` (built on `fetch_list`). Shipping methods are read zone by zone (`fetch_shipping_methods`), all or none, and come with `gone`: the zone methods mapped that the shop no longer has, which the form names and keeps. `WooCommerce Customer Decision` is the log of what was decided about Customers that looked like one buyer (see Possible duplicates); only code makes them (`in_create`), and deleting a Not the Same brings its suggestion back. `WooCommerce Order Import` holds an import's shop, date range, Make Delivery Notes tick, serial number file and Payment Method Map (each method's Mode of Payment, Bank Account and Payment Date, When Paid or When Completed), and its counts; a new one copies the map of the shop's last import, else reads the shop's gateways (`WooCommerceServer.fetch_payment_methods`). Only code makes its `WooCommerce Order Import Log` rows (`in_create`), and deleting the import deletes them. `Item WooCommerce Server` is a child table on `Item` (a custom field of `custom_fields.py`) that links an Item to its WC ID per server. `WooCommerce Settings` is a Single doctype for global sync options, and the email domains the Duplicate Customers report doesn't group by.

## Gotchas

- Patches live in `patches/v1/` and are listed in `patches.txt`. Add one there for data migrations, not an inline `migrate` hack.
- The custom fields on ERPNext's doctypes are defined in `custom_fields.py`, not in fixtures. `install.py` makes them on install and brings them up to date after every migrate (`create_custom_fields` saves only those that differ), so changing one needs no patch. They are system generated: Customize Form saves changes to them as Property Setters and won't delete them. A field removed from `custom_fields.py` stays on existing sites until a patch deletes it (see `remove_sales_order_link_fields`). The hook runs after the patches, so a patch that needs a new field makes it itself with `create_custom_fields`. A custom field without `insert_after` goes to the top of the form (`Meta.sort_fields`), which is how the Customer's WooCommerce sections get there; only one of them may lack it.
- A Single's new field gets its JSON default only while the Single has no values stored (`Document.load_from_db` makes a new doc then), and `get_single_value` gives `""` for a field never stored. A site that has saved the Single needs a patch to get the default (see `set_ignore_email_domains`).
- Doctype Python files have an auto-generated `DF` types block. Don't hand-edit inside it. Saving the DocType in the desk regenerates it in developer mode, but `bench migrate` doesn't, as it imports the JSON with `frappe.flags.in_import` set. After editing the JSON, run `TypeExporter(frappe.get_doc("DocType", name)).export_types()` from `frappe.types.exporter` in `bench console` (piped input works), then let ruff format it.
- A doctype test module makes the test records of every doctype its doctype links to, which clashes with ERPNext's (duplicate "Standard Buying"). Tests that only build docs in memory set `IGNORE_TEST_RECORD_DEPENDENCIES`.
- Frappe 16's `IntegrationTestCase` rolls back once a test class is done (`addClassCleanup`), not after each test. Tests that make records and look them up again roll back to a savepoint of their own, as `TestCustomer` in `test_sync_sales_orders.py` does.
- ERPNext's `Customer.on_update` saves the Customer's primary Address (`is_primary_address`, "ensure") whenever the Customer is saved, so that Address's `modified` changes though the sync never edits it.
- Rename in the desk merges in a background job (`update_document_title` with `enqueue`), and calls `before_rename` twice, in the request and again in the job; `after_rename` runs once. So a merge is recorded in `after_rename`, which runs before Frappe removes the merged document.
- With Customers named by their name, ERPNext's `Customer.after_rename` names the kept Customer of a merge after its ID ("Jan Kowalski - 1"). `record_merge` puts its name back.
- Whitelisted methods check argument types against their annotations in tests too, so pass ids as `str` where the signature says `str`.
- Frappe's Error Log is a MyISAM table, so what `frappe.log_error` writes stays through a rollback, unlike the InnoDB Integration Requests, which the API client therefore writes with `deferred_insert`.
- ERPNext's `update_child_qty_rate` (Update Items) takes a row sent without a description for a changed row and empties its description, so `update_sales_order_items` sends each row's own.
- Saving a template Item makes ERPNext copy its mandatory fields and those Item Variant Settings lists (weight, item group, brand and some 70 more) to all its variants (`Item.update_variants`, in a job after commit beyond 30 variants), unless `flags.dont_update_variants` is set. A template whose value differs from its variants' undoes theirs on its next save.
- A save rewrites text with markup: ERPNext's `Item.validate_description` cleans the description of the tags it doesn't keep (Stock Settings `clean_description_html`, on by default), then Frappe's `_sanitize_content` sanitises every field with `<` or `>`. Compare a mapped value with what an Item keeps through `as_saved`.
